# MOM_TEST_QUESTIONS.md

## Scopo

Validare se Auditor puo diventare offerta di audit tecnico o compliance software, invece di restare tool interessante. La domanda chiave e' se qualcuno paga per report, rischio ridotto o evidenza verso cliente.

## Chi intervistare

- CTO.
- Tech lead.
- Security/compliance manager.
- Responsabili delivery.
- Aziende con audit cliente o due diligence.

## Regole Mom Test

- Chiedere incidenti, bug, audit e debito tecnico recente.
- Non parlare di motore static analysis.
- Capire se preferiscono tool o report professionale.
- Cercare trigger esterni: cliente, compliance, acquisizione, handover.

## Domande

1. Come fate oggi code review o audit architetturale?
2. Qual e' stato l'ultimo bug o debito tecnico costoso?
3. Avete audit richiesti da cliente, compliance o acquisizione?
4. Che strumenti static analysis usate?
5. Paghereste piu per tool o per report professionale?
6. Quale parte del codice vi preoccupa di piu?
7. Quando avete scoperto troppo tardi un rischio tecnico?
8. Chi legge e usa i report di qualita codice?
9. Quanto costa oggi una revisione architetturale esterna?
10. Che evidenza vi servirebbe per convincere management o cliente?

## Segnale buono

- Audit richiesto da cliente o compliance.
- Debito tecnico con costo concreto.
- Interesse per report senior.
- Budget gia speso in quality, security o consulenza.

## Segnale di stop

- Curiosita tecnica senza budget.
- Nessun trigger esterno.
- Team non legge report.
- Vogliono solo tool gratuito.

## Prossima azione

Proporre un audit pilota su repo piccolo. Se il mercato vuole report e non tool, posizionare Auditor come asset di consulenza.
